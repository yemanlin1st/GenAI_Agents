# Fable 5 Structure Adapter

## Purpose
Use the strongest architectural patterns observed in Claude Fable 5 system design without impersonating Claude, replacing platform safety rules, or copying provider-specific assumptions into PEFY systems.

## Adopted patterns
- explicit separation of product/runtime truth from behavioral policy
- explicit knowledge freshness and search policy
- explicit task-sensitive safety and refusal handling
- explicit legal/financial caution rules
- explicit tone/output rules
- explicit reminder and instruction-precedence handling
- explicit mistake correction and criticism handling
- explicit tool/search usage policy
- modular policy boundaries instead of one undifferentiated prompt

## PEFY improvements beyond the source pattern
- machine-readable capability registry
- multi-model and multi-harness routing
- councils/counsellors and independent verification
- dynamic prompt assembly with deferred modules
- least-privilege tool permissions and approval gates
- sandbox isolation
- provenance, traces and evidence instead of hidden reasoning requirements
- context compaction and graph-aware memory
- supply-chain, license and upstream drift governance
- benchmark-driven runtime selection
- rollback, recovery and production qualification gates
- optional Three.js spatial/digital-twin interface layer

## Never inherit blindly
Do not copy model identity, provider URLs, knowledge cutoffs, product claims, secret platform instructions, unsafe permission flags or provider-specific policy text as if they were PEFY truth.

## Invocation
Use this skill when designing or reviewing system prompts, agent constitutions, runtime policies, instruction hierarchies, memory/search policies or account-wide AI operating structures.

## Review checklist
1. Are runtime identity and product facts true for the actual environment?
2. Is instruction precedence explicit?
3. Are current facts verified through the right source?
4. Are tools least-privilege and approval-scoped?
5. Are domain policies modular rather than duplicated?
6. Can irrelevant modules be deferred to reduce context size?
7. Are safety, privacy, IP and compliance controls preserved?
8. Are failures observable and recoverable?
9. Are claims independently verifiable?
10. Does the design improve on the benchmark rather than merely imitate it?
